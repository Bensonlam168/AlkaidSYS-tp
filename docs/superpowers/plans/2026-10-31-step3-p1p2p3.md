## Task 2（W2）：P1-B 修复两个不可信的 RateLimit 测试

**Files:**
- Modify: `tests/Feature/RateLimitMiddlewareTest.php`
- Modify: `tests/Unit/Infrastructure/RateLimit/RateLimitServiceTest.php`

**Interfaces:** 无生产代码改动

- [ ] **Step 1: 复现两个失败的独立行为**

```bash
docker exec alkaid-backend ./vendor/bin/phpunit --filter test_exceeding_limit_returns_429_and_sets_rate_limited_flag   # 预期 FAIL（120 次请求 vs capacity 100，实测 200）
docker exec alkaid-backend ./vendor/bin/phpunit --filter test_tokens_refill_over_time                                   # 预期 PASS（时序敏感）
```

- [ ] **Step 2: 让 429 用例确定性成立**

`RateLimit::handle()` 每次请求都读 `config('ratelimit')`（`app/middleware/RateLimit.php:31`），因此测试可以在用例内覆盖配置：

```php
Config::set(['scopes' => ['ip' => ['enabled' => true, 'limit' => 5, 'period' => 60, 'capacity' => 5, 'rate' => 0.001]]], 'ratelimit');
Cache::clear();
```
再发 10 次请求，断言最后一次 429。`tearDown()` 恢复原配置（保存 `setUp` 前的 `config('ratelimit')` 原值并写回）。

**不要**改 `phpunit.xml` 的全局限额——那会污染整个测试套件。

- [ ] **Step 3: 让 refill 用例容忍慢环境**

把单次 `sleep(1)` + 立即断言，改为带重试的轮询（最多等 5 秒，每 100ms 试一次），第一次成功即通过；超时才失败。不改变被验证的语义（令牌会随时间补充），只去掉对精确时序的依赖。

- [ ] **Step 4: 验证**


**Interfaces:**
- Produces: `WorkflowTaskController::assertUserExistsInTenant(int $userId, int $tenantId): void`（不存在则抛业务异常/返回 422）

- [ ] **Step 1: 写失败测试（校验缺失）**

`WorkflowTaskTransferValidationTest`：播种一个任务（反射注入 `self::$tasks`）+ 权限，`POST /v1/workflow/tasks/:id/transfer` 传一个**不存在的** `target_user`，断言响应码不是 500、且业务码为 422/400、且 `self::$tasks[$id]['assignee']` **未被改写**。

- [ ] **Step 2: 跑测试确认失败**

预期：当前实现无校验，`assignee` 被写成不存在的用户（若后续加外键则 500）。

- [ ] **Step 3: 实现校验**

在 `transfer`/`delegate` 里，赋值前查 `users` 表（限定当前租户）：

```php
$exists = Db::name('users')->where('id', (int) $targetUser)->where('tenant_id', $tenantId)->count();
if (!$exists) { return $this->validationError(['target_user' => '目标用户不存在或不属于当前租户']); }
```
`target_user` 需为纯数字（`ctype_digit`），否则同样拒绝。

- [ ] **Step 4: 移除 null 宽免**

4 处形如 `... === $tenantId || ... === null` 的条件，去掉 `|| ... === null` 分支。
理由：DB 层 `tenant_id` 是 `NOT NULL`，`null` 永不成立，属死分支；保留会误导读者以为支持"全局记录"。

- [ ] **Step 5: 写失败测试（严格化后仍隔离）**

`WorkflowTenantStrictnessTest`：两个租户各一个任务，用租户 A 的 token 读租户 B 的任务 → 必须 403/404；读自己租户的 → 200。**这条同时验证移除宽免没有破坏正常路径。**
