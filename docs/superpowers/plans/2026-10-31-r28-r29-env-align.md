## Review Focus

- **`.env` 优先级高于容器环境变量**（已实测）：`think\Env::get()` 先读 `$this->data`（由 `Env::load('.env')` 填充），只有缺失时才回落 `$_ENV`/`getenv('PHP_*')`。所以 `.env.example` 里写错的 `DB_HOST=127.0.0.1` 会**真的覆盖** compose 注入的 `mysql`，不是"反正 compose 会赢"。
- **`DB_CHARSET` 也要对齐**：`.env.example` 是 `utf8`，实际是 `utf8mb4`；utf8 存不了 emoji/部分 CJK。
- **不要给 `DB_*` 加 force**（同 R27 的裁定）。
- **t048/t050 是否要补 `CACHE_FILE_PREFIX`**：这两个配置缺它，用它们跑测试时 R20 的保护不存在（`Cache::clear()` 会删整个 `runtime/cache`）。

## Task 1：R28 给 t048 / t050 补 force

**Files:**
- Modify: `phpunit.t048.xml`
- Modify: `phpunit.t050.xml`

**已核实事实**
- `phpunit.t048.xml` 的 env：`APP_ENV`、6 个 `DB_*`、`ALLOW_RUNTIME_DDL`（8 条，无 `CACHE_FILE_PREFIX`、无限流配置）
- `phpunit.t050.xml` 的 env：`APP_ENV`、6 个 `DB_*`（7 条）
- 两者都没有 `force`，因此同样会被 shell 导出变量抢占（R27 的全部危害都适用）
- `phpunit.xml`（R27 已改）的 force 策略：force 10 个（`APP_ENV`、`ALLOW_RUNTIME_DDL`、`CACHE_FILE_PREFIX`、`RATELIMIT_ENABLED` + 6 个 `RATELIMIT_SCOPE_*`），`DB_*` 一律不 force

**要做**
- 按「存在则加 force」原则：
  - t048：`APP_ENV`、`ALLOW_RUNTIME_DDL` 加 `force="true"`
  - t050：`APP_ENV` 加 `force="true"`
- **`DB_*` 一律不加 force**，并在两个文件里各写一段与 `phpunit.xml` 一致的说明注释（含「`.env` 优先级更高」这一实测事实）
- **额外决定项（需你判断并给理由）**：是否给两者补上 `CACHE_FILE_PREFIX`（带 force）以保持与 `phpunit.xml` 一致的 R20 保护？我的倾向是**补**，因为不补就等于「用这两个配置跑测试时 `Cache::clear()` 会删整个缓存目录」。若你判断不该补，说明理由。

**验证**
- 改前/改后对照：导出 `APP_ENV=production` 分别用两个配置跑一个鉴权测试，改前应被打挂、改后应通过
  （命令形如 `docker exec -e APP_ENV=production alkaid-backend ./vendor/bin/phpunit -c phpunit.t048.xml <测试文件>`）
- 用 `-c phpunit.t048.xml` / `-c phpunit.t050.xml` 各跑一次 `tests/Unit`（或它们各自声明的 testsuite），
  给出结果，证明配置可正常解析
- 若补了 `CACHE_FILE_PREFIX`：用 `-c phpunit.t048.xml` 跑一个会调 `Cache::clear()` 的用例，
  在 `runtime/cache` 放根层哨兵，验证哨兵幸存

## Task 2：R29 `.env.example` 与容器部署形态对齐

**Files:**
- Modify: `.env.example`

**已核实事实（这 5 个键全部与容器不一致，任一都会误导）**
| 键 | `.env.example` 现值 | 本地 `.env` / compose 实际 |
|---|---|---|
| `DB_HOST` | `127.0.0.1` | `mysql`（compose 服务名；且 compose 也为 backend 注入该 env） |
| `DB_NAME` | `test` | `alkaid_sys`（compose `MYSQL_DATABASE`） |
| `DB_USER` | `username` | `root` |
| `DB_PASS` | `password` | `root`（compose `MYSQL_ROOT_PASSWORD`） |
| `DB_CHARSET` | `utf8` | `utf8mb4` |

**实证（必须复核）**
- `think\Env::get()` 先读 `.env` 填充的 `$this->data`，再回落 `$_ENV`
- 临时把 `.env` 的 `DB_HOST` 改成 `127.0.0.1` → `env('DB_HOST')` 与 `config.database.connections.mysql.hostname` 都变成 `127.0.0.1`
- 而容器内连 `127.0.0.1:3306` 实测 `SQLSTATE[HY000] [2002] Connection refused`

**要做**
- 把上述 5 个键改为与 compose 本地开发形态一致
- 在 DB 段上方加一段警示注释，样式参照文件里已有的 `JWT_SECRET` 注释：
  - 这些是 **docker compose 本地开发默认值**
  - 生产部署必须替换（`DB_HOST` 改成实际主机、`DB_PASS` 改强密码）
  - 并写明「`.env` 的优先级高于容器环境变量」，所以改错会覆盖 compose 的注入值
- 若你认为 `DB_USER`/`DB_PASS` 保持占位更好（安全考量），说明理由并提出替代方案（例如注释里给出 compose 默认值）

**验证**
- `cp .env.example /tmp/env_probe && diff` 形式，逐键对比改后 `.env.example` 与本地 `.env` 的 DB 段，
  列出**完全相同**与**有意不同**的键（本地 `.env` 可能有额外项，如 `APP_ENV`）
- 用一个临时目录模拟新检出：把 `.env.example` 复制为 `.env` 后，在容器内解析
  `config.database.connections.mysql.hostname` —— **必须得到 `mysql`**
  （**不要**污染仓库的 `.env`：改完立刻还原，并用 `git status` 确认 `.env` 未被跟踪、内容已复原）
- 三处门禁 exit=0
