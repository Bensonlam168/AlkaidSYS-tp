## Task 1：R23 工作流测试夹具隔离

**Files:**
- Create: `tests/Traits/WorkflowFixtureIsolation.php`
- Modify: `tests/Feature/Workflow/WorkflowDefinitionValidateEndpointTest.php`
- Modify: `tests/Feature/Workflow/WorkflowInstanceHistoryTypeTest.php`
- Modify: `tests/Feature/Workflow/WorkflowTaskClaimAuthorizationTest.php`
- Modify: `tests/Feature/Workflow/WorkflowTaskTransferValidationTest.php`
- Modify: `tests/Feature/Workflow/WorkflowTenantIsolationTest.php`
- Modify: `tests/Feature/Workflow/WorkflowTenantOwnershipTest.php`
- Modify: `tests/Feature/Workflow/WorkflowTenantStrictnessTest.php`
- Modify: `tests/Feature/Workflow/WorkflowTriggerLogTypeTest.php`

**已核实根因**
- `permissions.slug` 上有唯一索引 `idx_slug`；
- **6 个测试类共用同一批 slug**（`workflow.task.read`、`workflow.definition.read` 等）却用**不同固定 ID**（6101/6201/6301/6421/6521/6631/6721…）；
- 各类的 `seedFixtures()` 只在**自己**范围内「先清理再插入」，清不掉**别的类**留下的同 slug 行；
- PHPUnit 在 `setUp()` 抛异常时**不执行 `tearDown()`** → 一次失败就把残留留给后续所有运行，形成级联失败，需手工清库才能恢复。

**Trait 接口（新建 `Tests\Traits\WorkflowFixtureIsolation`）**
- `protected function purgeWorkflowFixtures(): void`
  —— 在 6000–6999 区间内按自然键清理测试夹具：
  `permissions`（slug LIKE 'workflow.%' 或 id 在区间内）、`role_permissions`、`user_roles`、`roles`（slug LIKE 'wf\_%' 或 id 在区间内）、`users`（email LIKE '%@workflow-%' 或 id 在区间内）。
  **必须限定区间**，避免误删真实数据。
- `protected function seedWorkflowFixtures(callable $seed): void`
  —— 先 `purgeWorkflowFixtures()`，再 `try { $seed(); } catch (\Throwable $e) { $this->purgeWorkflowFixtures(); throw $e; }`
  —— 保证 setUp 阶段失败不留残留。

- [ ] 新建 trait，并在 8 个测试类中 `use WorkflowFixtureIsolation;`
- [ ] 各类的 `seedFixtures()` 改为调用 `seedWorkflowFixtures(function () { ...原播种逻辑... })`
- [ ] 各类的 `cleanupFixtures()` 改为调用 `purgeWorkflowFixtures()`（或在其内部叠加）
- [ ] **验证**：在一个测试类里临时注入「setUp 中途抛异常」的残留（写入一组同 slug 但不同 ID 的行），
      然后跑**另一个**测试类 → 必须通过（证明跨类残留被清掉）。跑完把注入的残留删掉。
- [ ] 全 `tests/Feature/Workflow/` 全绿，且**连续跑两次**都绿

## Task 2：R20 让测试缓存清理只作用于测试子树 + M7 失败原因归类

**Files:**
- Modify: `config/cache.php`
- Modify: `phpunit.xml`
- Modify: `app/middleware/Auth.php`

**R20 已核实**
- `File::clear()` 的实现是 `rmdir($this->options['path'] . $this->options['prefix'])`
- `config/cache.php` 的 file store 目前 `'prefix' => ''` → clear() 删的是**整个** `runtime/cache`
- 仍有 8 个测试文件共 16 处调用 `Cache::clear()`

**R20 做法**
- `config/cache.php` 的 file store：`'prefix' => env('CACHE_FILE_PREFIX', '')`
- `phpunit.xml` 的 `<php>` 段加 `<env name="CACHE_FILE_PREFIX" value="test"/>`
- 这样测试环境里 `Cache::clear()` 只删 `runtime/cache/test/`，**不必改 8 个测试文件**
- 生产/开发不设该 env → 行为不变

**M7 已核实**
- `app/middleware/Auth.php` 按异常消息子串归类 reason（`expired` / `revoked` / `decode`），
  其余一律 `token_invalid`；`INVALID_TENANT_SCOPE` 落进兜底，日志里与「格式错误」不可区分

**M7 做法**
- 增加一条分支：消息含 `INVALID_TENANT_SCOPE` → `reason = 'invalid_tenant_scope'`
- **不得**改变 errorCode/errorMessage 的既有取值（仍 401/2001 + `error.token_invalid`），只改日志 reason

- [ ] 改配置与 phpunit.xml
- [ ] 改 Auth 归类
- [ ] 验证 R20：全量跑前后 `runtime/cache` 目录**仍存在**，且其下出现 `test/` 子目录
- [ ] 验证 R20 反向：临时删掉 phpunit.xml 的 env → `Cache::clear()` 又会删整目录（证明改动真的起作用）
- [ ] 验证 M7：构造一个 `INVALID_TENANT_SCOPE` 的失败请求，确认日志里 reason 是 `invalid_tenant_scope`，
      且响应仍是 401 + code 2001
- [ ] 回归：`tests/Integration/Permission/`、`tests/Unit/Auth/`、`tests/Unit/Lowcode/` 全绿
