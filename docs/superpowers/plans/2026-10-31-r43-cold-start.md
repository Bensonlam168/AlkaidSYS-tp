## 一、实测结论：冷启动阻塞有**两处**，不是一处

### 证据：现状必然失败

```
# 全新库 alkaid_r43_probe，执行 php think migrate:run
[think\db\exception\PDOException]
SQLSTATE[42S02]: Base table or view not found:
  1146 Table 'alkaid_r43_probe.permissions' doesn't exist
# 失败后库里只有 1 张表：migrations（Phinx 懒创建，0 行）
```

### 阻塞 B1：8 位版本号（R43 字面所指）

| 事实 | 数据 |
|---|---|
| 文件 | `database/migrations/20251125_add_casbin_manage_permission.php` |
| 版本号 | `20251125`（**8 位**），全仓库唯一；其余 34 个都是 14 位 |
| 排序后果 | 数值 20,251,125 ≪ `20251119000001` = 20,251,119,000,001 → Phinx 让它**第一条**执行 |
| 依赖 | 它写 `permissions` 表，而该表由 `20251119210400_create_permissions_table.php` 创建 |
| 结论 | 必然失败 |

### 阻塞 B2：硬编码 `role_id = 1`（改完 B1 才会暴露）

| 事实 | 数据 |
|---|---|
| 文件 | `database/migrations/20251219000002_add_dept_and_menu_permissions.php` |
| 代码 | `INSERT INTO role_permissions (role_id, ...) SELECT 1, p.id, NOW() FROM permissions p ...` |
| 依赖 | `role_permissions.role_id` 有外键 → `roles.id`；而全新库**没有任何角色**（也没有租户） |
| 结论 | 报 `1452 fk_role_permissions_role_id` |

**验证过程**（我亲自执行，探针库已删除）：

1. 只把 B1 的文件名改成 `20251126000001_...` → 新库建出 **26 张表**、`casbin.manage` 成功插入，但随后在 `20251219000002` 报 1452
2. 再往探针库插入 `tenants(id=1)` + `roles(id=1)` → 整条链跑完：**35 个迁移全部应用、29 张表**

→ 即冷启动阻塞恰好是这两处；修掉它们，新库可以从零建起来。

## 二、B1 的选项

| 选项 | 做法 | 对既有库的影响 | 评价 |
|---|---|---|---|
| **A1（推荐）** | 重命名为 `20251126000001_add_casbin_manage_permission.php`（14 位，保留 2025-11-26 的历史时序；类名 `AddCasbinManagePermission` 不变） | 新版本对既有库是「未应用」→ `migrate:run` 会跑它 → **该迁移 `up()` 本身已是幂等**（先查 `slug='casbin.manage'` 存在则跳过）→ 无副作用。<br>遗留一行 `version=20251125` 的旧记录（无对应文件）——惰性无害：`migrate:status` 按文件列、`check-migrations` 的 B 用 `max(applied)` 不受影响 | 一个文件、永久正确 |
| A2 | 重命名到**链尾**（如 `20251225000001_...`） | 同上（也是未应用 → 幂等跳过） | 同样可行，但丢失「它其实发生在 2025-11-26」的时序信息 |
| B | 保留文件名，加 `if (!$this->hasTable('permissions')) return;` 守卫，再新增一个链尾迁移补插权限 | 既有库行为不变 | **两个文件**，且「错位版本号」这个坏示范留在仓库里，后来者可能照抄 |
| C | 引入 schema 基线 dump | 需要维护基线 | 过重，本项目无此基建 |

**推荐 A1**，理由：迁移已幂等 → 改名的风险接近零；一个文件解决；时序最诚实。

## 三、B2 的选项（这一处需要你拍板，因为它牵涉引导流程的设计）

### 背景事实

- `database/seeds/CorePlatformSeed.php` **会**创建 tenants / roles / permissions 并分配权限
- 但它的分配是**硬编码权限 ID 1..20**：`for ($i = 1; $i <= 20; $i++) {... 'permission_id' => $i ...}`
- `dept.*` / `menu.*` 这 6 个权限由 `20251219000002` 创建，自增 ID 在 20 之后 → **seeder 不会分配它们**
- 所以迁移里那段「分配给 role 1」是**必需的**，不能简单删掉

→ 形成了鸡生蛋：**迁移需要角色存在，而角色由 seeder 创建；seeder 又需要迁移已建出 permissions**。

### 选项

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **X1（推荐）** | ① 迁移里的 role 分配改为**容错**：`... AND EXISTS (SELECT 1 FROM roles WHERE id = 1)`（角色不存在则跳过分配，权限照常创建）<br>② **同时改 seeder**：把硬编码 `1..20` 改为 `INSERT ... SELECT id FROM permissions`（动态分配全部权限、且 `NOT EXISTS` 幂等） | 冷启动 `migrate:run` 不再失败；`migrate + seed` 后管理员拥有**全部**权限（比现在更正确）；既有库跑 seeder 会补齐缺失的 dept/menu 授权 | 需改两个文件；seeder 行为变化需回归（它目前可能被测试依赖） |
| X2 | 只做 ①（迁移容错），不动 seeder | 改动最小 | 新库上 `dept.*`/`menu.*` 权限**永远不会**分配给管理员 → 管理员进不了部门/菜单管理页。等于把一个「启动失败」换成「启动成功但功能缺失」，更难发现 |
| Y | 迁移里**顺带创建** tenant 1 + role 1（`INSERT ... WHERE NOT EXISTS`），再做分配 | 单靠 `migrate:run` 就能得到可用库 | 让迁移承担业务种子数据职责；与 seeder 的 tenant/role 创建冲突，需要追加幂等改造；争议较大 |
| Z | 修 B1 后**不管** B2，把「冷启动」定义为 `migrate:run` + 手工插入 base data | 零改动 | `migrate:run` 仍然会**失败中断**，必须改代码或文档；不解决 |

**推荐 X1**。它把「启动失败」变成「启动成功且 seeder 后功能完整」，并且顺带修掉 seeder 硬编码权限 ID 这个同类隐患。
