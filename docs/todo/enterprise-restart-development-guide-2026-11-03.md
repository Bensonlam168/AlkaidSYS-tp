## 1. 先采用的开发判断

保留 PHP/ThinkPHP/Swoole、现有 Domain/Infrastructure 和 web-antd，按模块化单体继续重建。保留本轮测试隔离、CI、授权子集、租户参数和事件日志成果。以可持久的实际业务链为验收单位，暂停无边界的大范围功能扩展。

开发分成三个门槛：G0 为安全开展整改，当前主要具备；G1 为选定范围可正常开发，需要资源、会话和发布契约闭环；G2 为企业生产发布，需要运行、恢复、安全、容量和交付证据。报告的评审通过只能代表对应包，不得自动提升整个系统门槛。

当前第一优先级是评审 RV-01～RV-06，以及生产产物 RV-12～RV-15。工作流是否进入第一版本是产品范围决策，不能默认以完整工作流生态作为重启前提。

## 2. 工作组织与完成定义

每个开发包指定一个负责人、独立分支/PR、设计依据、风险场景、验收记录和遗留项。采用仓库要求的带 scope Conventional Commits，禁止把格式化、第三方代码搬迁和授权语义修改混成一个难以评审的大补丁。

任务只有同时满足以下条件才可标记完成：

1. 设计/规范先对齐；如改变平台主体、物理模型、Schema 发布或队列契约，必须有已接受 ADR。
2. 触发条件对应的失败用例能证明旧行为，修复后行为通过；安全/并发路径使用真实边界而不只 mock 掉关键判断。
3. 相关回归与门禁实际执行，记录 SHA、环境、命令、退出码、测试数、skip/incomplete 和豁免。
4. 文档与能力台账更新；暴露入口的承诺与实现一致。
5. 独立评审关闭对应 P0/P1；涉及上线的包再提供发布/回退/恢复证据。

不得用“代码存在”“单测全绿”“已推送”“error 数下降”单独作为完成定义。测试失败应定位根因；性能预算可以独立套件，但行为断言必须保留。

## 4. W0：把现状变成可使用的开发基线

**输入**：评审报告第 4 节 ER 映射、[未决台账](open-items-2026-11-03.md)、[阶段 A 历史计划](../superpowers/plans/2026-10-31-phase-a-verification-baseline.md)。历史计划只执行了部分内容，不能把其任务标题当完成记录。

交付一张持续维护的能力表，至少包括：能力、首期是否承诺、入口/feature gate、实现状态、源码证据、最新测试/演练证据、阻断项、负责人、下一决策。状态建议统一为“已验收 / 部分实现 / 未实现 / 首期关闭 / 已废弃”，不再使用无权重完成百分比。

将原台账的远端分叉、已修 CI、插件 DI、生产镜像和当前风险拆开记录。更新事实可以直接做，不需要把每个旧数字当产品决策。历史报告保留快照，当前入口明确指向最新评审。

验收环境必须分开数据库账号及授权、Redis/队列命名空间、文件目录和 DDL 对象；库名含 `_test` 不应是唯一防护。对主进程、CLI 子进程、后台任务分别确认配置来源。临时环境文件不得泄漏凭据，异常中断也要清理。

建立三个清单：常规 PR 回归、涉及数据/身份的扩展回归、发布演练。CI 已有 739 个默认测试的真实证据；812 全量和插件 24 errors 作为不同口径登记。明确 3 skipped/3 incomplete 的用例、原因与到期日，不应机械禁止任何合理 skip，也不允许长期无人负责。

## 5. W1：收敛完整授权和会话，而非只修赋权接口

### 5.1 W1-A 主体管理和会话失效

设计/规范先回答：租户管理员能管理哪些用户、是否允许管理与自己权限相等的账号、平台账号如何隔离、强制重置和账号恢复何时吊销全部会话。由统一应用服务处理，不在多个控制器复制角色表查询。

最低实现与验收：

- 密码、登录标识、MFA、状态、角色调整均检查“目标主体可管理性”；低权限 `user.write` 不能重置高权限账号。
- 持久会话版本或安全戳覆盖 Access/Refresh，密码变更、强制登出、停用/恢复遵守同一吊销规则。
- 最终 tenant/site 来自已验证身份；显式头冲突按规范拒绝，不能校验一个上下文后切换到另一个。
- site 校验包含存在、归属、状态与用户授权，明确 `0` 全局桶语义。仅同租户不代表用户可进入所有站点。
- 对缺失头、正确头、冲突头逐一测试；对数据库/缓存故障区分 500/503 与 401/2001，不能把基础设施故障伪装成退出登录。

所需设计输出：主体管理规则表、会话失效事件矩阵、身份上下文解析时序、错误码/日志字段。平台与租户的权限目录边界使用 ADR，不能靠给 admin slug 特判解决。

### 5.2 W1-B 原子刷新和撤权传播

Refresh 设计必须明确原子消费、后继登记、失败重试、并发请求以及重用后的 family 处理。选择 Redis 原子脚本或数据库事务/锁等方案时，先说明故障恢复语义，再写实现。

撤权不能只做删缓存：把权威权限版本与缓存绑定，防止旧 fetch 在清除后回写。对关键操作明确撤权生效时限和版本源不可用时的安全行为。版本的读写必须与授权事实变更协调，不能引入一个同样有旧值窗口的无约束版本缓存。

验收必须包括同一 Refresh 多进程同时消费、旧权限 fetch 被屏障暂停后发生撤权、缓存删除失败、依赖恢复、跨 worker 与跨实例。顺序单进程断言作为回归保留，但不替代这些场景。

### 5.3 W1-C SQL 与请求边界

统一约束集合名、物理表名、字段名、索引名、关系目标及 SQL 可选属性；数据值参数化，标识符按允许规则构建。拒绝核心表、保留列和未授权物理映射，不能只在 HTTP 控制器校验。

将 RateLimit 和 AccessLog 的客户端 IP 解析收敛到统一可信代理组件。认证前只按可信 IP/登录账号限制；认证后再用真实 user/tenant 做配额。白名单不得依据尚未认证的租户头绕过安全限制。

验收使用正常建模与反例输入直接调用 HTTP、Service、SchemaBuilder 和迁移生成器。任何拒绝分支须证明没有发生数据库/缓存/事件副作用。

## 6. W2：先定物理所有权，再建设 Schema 发布

### 6.1 必须先形成的 ADR

| ADR 主题 | 必须明确的内容 | 不可接受的替代 |
| --- | --- | --- |
| 动态实体物理资源 | 租户/site/应用作用域；共享同构还是租户独立；表所有者与引用；自定义表名；历史映射升级 | 仅把默认表名前加 tenant 前缀就宣布完成 |
| Schema 生命周期 | 草稿、发布版本、兼容规则、迁移计划、应用记录、激活、失败恢复、并发控制 | 将 MySQL DDL 放普通事务里期待整体回滚 |
| 数据授权 | 模型、记录、字段，平台操作与租户操作；导出、批量和后台任务统一策略 | 用前端隐藏替代服务端授权 |
| 删除/保留 | 删除集合、删除租户数据、归档与物理销毁的不同权限和执行步骤 | 默认 drop_table=true |

ADR 应列选项、适用场景、成本、决策、迁移与回退影响；本指引不预先批准破坏性历史结构改造。没有业务证据时默认收窄首期范围，例如只支持一个明确的租户模型策略，并关闭其他入口。

### 6.2 实施顺序与验收

先封闭任意物理映射和删除入口；在副本盘点现有映射及 Schema 差异；再实现发布计划与状态、版本并发控制、DDL 应用和激活；最后开放前端建模和数据写入。

故障注入覆盖：DDL 成功后元数据失败、版本冲突、提交前后崩溃、缓存失败、事件失败、应用中断重入。不能把异常吞成 version 0 后继续宣称发布成功。`migration:diff --all` 要遍历全部分页，超过 20 个集合必须有反例。

字段更新必须实际应用更改；不支持的变更返回明确不可用，不允许只发“updated”事件。表单 tenant 先严格校验再持久化，直接服务调用同样测试零写入。

历史 `20251125` 账本按仓库既有 dry-run→备份非空→指定版本协调→全量检查→移除豁免流程处理；本次评审没有授权盲删账本。上线还要验证空库安装、旧库副本升级、重入、回退或向前修复策略，不得用 CI 新库成功代替旧库验收。

## 7. W3：干净检出必须能得到可运行产物

### 7.1 W3-A 依赖和镜像

先处理 composer json/lock 一致性，再分批升级安全公告涉及的生产依赖。每批记录锁定前后版本和回归；如果公告在本应用不可达，给有期限的书面例外。供应链扫描应按真实发布范围阻断，不能继续一概 warning。

Docker 构建全过程不得启动应用去连接 Redis/MySQL；服务发现、发布资源等步骤要有明确替代位置。检查不可变产物中自有类和所选插件依赖都能加载，平台扩展满足要求，真实环境文件和测试产物不在镜像内。

验收链：干净检出→冻结依赖安装→镜像 build→无源码挂载启动→配置预检→liveness/readiness→身份/权限/低代码冒烟→重启恢复。将镜像 digest 绑定提交和验收记录，发布同一产物，不在生产重新 composer update。

### 7.2 W3-B 配置、入口和日志

消除 production overlay 继承的 DB_HOST/REDIS_HOST/RABBITMQ_HOST 覆盖。配置测试必须输入有意不同的外部地址，以最终 compose 渲染及运行期有效值为准，输出脱敏信息。

根据真实拓扑生成 Nginx/网关配置：TLS 在何处终止、生产域名、CORS、可信代理、后端内网暴露、上传和超时。生产 Origin 的 OPTIONS 必须经真实网关验证，不能只测应用控制器。

应用与 Nginx 日志选择结构化 stdout/集中采集，或明确文件采集、卷、轮转与留存；至少能跨容器重建追溯 trace/user/tenant/site，记录真实可信 IP。对 `/readyz` 内网限制、错误详情脱敏和整体 deadline 做验收。日志不得包含 Token、明文密码及生产密钥。

### 7.3 W3-C CI 覆盖与保护

修前端 setup-node 的缓存类型与锁文件位置，Node 满足 engines，pnpm 使用 packageManager 的唯一来源；改为确实存在的类型检查脚本，确认 web-antd 构建产物位置。现有 echo 部署只算占位。

主 CI 保持 Unit、Feature、Legacy；将 Integration/E2E 与选定插件能力纳入合适的 PR/发布链。镜像和浏览器链路必须有实际运行结果。插件 standalone/host-required 可以合理分套，但两个承诺范围都要有明确执行位置；不能通过改默认 suite 把失败悄悄消失。

已有七项 required 应保留。管理员例外、main 是否要求最新基分支、PR review 与第二评审人由仓库维护者明确；不把配置文件存在当远端设置生效。新增 required 前先证明真实 CI 可成功且每次必须出现。

## 8. W4：只做一个真实业务切片

默认候选为“租户内申请单”；若业务方尚未选择，不必先实现审批平台。最小验收内容：

1. 平台建立租户与委派账号，租户用户登录，最终身份上下文可审计。
2. 按已接受策略定义集合与字段，发布 Schema，生成/应用迁移并激活版本。
3. 前端从表单详情取得后端 validator/parsed，填写、校验并保存。
4. 记录、列表、详情、修改、导出在真实用户/租户/site/字段权限下符合规则。
5. 更换 worker、重启进程和重新部署后，定义、数据、状态、历史仍正确。
6. 失败重试、重复提交、并发修改使用幂等/版本策略，不产生重复副作用。

若首期包含审批，再增加唯一工作流内核及不可变定义版本；Repository、任务、历史和数据操作节点必须真实持久化。停用未接通的演示入口，不能将 static 数组和随机 ID 当成功业务结果。

工作流优先补“定义发布→创建实例→产生任务→授权审批→状态变化→业务数据变化→审计恢复”契约。先为这条链挑出必要的服务，再处理容器短名/FQCN 别名、全局 owner、配置来源、节点 parser key 和宿主注入。DI 的三个选择应由设计提出可评审方案，业务方只决定影响产品范围的部分。

对关键事件采用持久投递与持久 DLQ；死信写入失败时保留原任务并退避告警。日志不能代替消息归宿。恢复后人工重放须有授权、审计和幂等，不能重复执行已成功监听器的业务副作用。

## 9. W5：企业生产发布证据门槛

| 证据 | 必须回答 | 交付材料 |
| --- | --- | --- |
| 安全边界 | 弱管理员、不同租户/site、旧会话、撤权并发均不能越过边界 | 自动化反例矩阵、独立 review 与剩余风险签收 |

| 运维控制 | 变更、回退、密钥轮换、租户删除有权限和操作步骤 | 发布/回退/轮换手册、演练结果与责任人 |

SLO、容量、数据分类、RPO/RTO 没有业务输入时先标“待决策”，不得编造企业级阈值。完成演练后再限定客户、数据量和流量逐步放量；只有证据覆盖的能力可以进入发布说明。

## 10. 命令使用与交接模板

### 10.1 当前可直接使用的只读自查

```bash
docker exec alkaid-backend php scripts/check-docs.php --strict
docker exec alkaid-backend php scripts/check-phpunit-config.php --strict
docker exec alkaid-backend php scripts/check-env-example.php --strict
docker exec alkaid-backend php scripts/check-migrations.php --strict
docker exec alkaid-backend php scripts/check-migration-data.php --strict
docker exec alkaid-backend php think lang:check
docker exec alkaid-backend php think route:verify --strict
docker exec alkaid-backend composer validate --no-check-publish --no-interaction
docker exec alkaid-backend composer audit --locked --no-dev --format=json --no-interaction
```

后两条在评审基线为失败，作为待修复输入保留。`check-rawsql-safety --strict` 是文本人工审查清单，不是已经验证的漏洞数；不要为了绿色删掉合法的显式跨租户系统查询或盲加 tenant。

主全量、Integration/E2E、性能和插件测试，应先确认独立资源及当前夹具，再按包执行。迁移、seed、账本 apply、容器 reload/restart、依赖升级和生产部署是实施动作，不是本指引已经执行的命令；每包按授权范围与仓库流程操作。

### 10.2 给下一位执行代理的任务模板

```text
任务包：W?-?；基线 SHA：填写实际值。
目标：写明一个用户/运维可观察的最终行为。
设计依据：Always Rules、具体技术规格/ADR、评审 RV 编号。

```
